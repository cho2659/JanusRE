3-0. 재배치 고려 필수

3-1. tt 모듈의 판별을 오버헤드 없이 수행하기 위해 Native CModule을 이용하여 offset으로 타겟 여부를 확인 가능하도록 비트맵을 만드는 로직을 만들것
이 경우 Process.attachModuleObserver(callbacks)을 활용하여 모듈의 로드와 언로드시 업데이트한다
이 또한 observe될 경우 잠시 프리즈 후 재개할 것

3-2. jmp 계열(jz, jnz 포함)의 추적을 위하여 함수 시작점 비트맵을 만들고 판별 가능하게 할 것
python 시작에서 부터 ghidra에서 타겟의 함수 시작 오프셋을 받아와 만들 것, 트레이스 시작 버튼 클릭 후에도 아직 비트맵 완성이 안되었다면 프리즈할것
이 경우 Process.attachModuleObserver(callbacks)을 활용하여 타겟 모듈의 로드와 언로드시 업데이트한다
이 또한 observe될 경우 잠시 프리즈 후 재개할 것

4-1. 프리다의 transform을 통해 다음을 구현
세 개 변수를 설정한다

dst (offset 형태)
src (offset 형태)
is_jump (bool 형태)

타임라인 별로 설명하겠다
i.
dst 0xoffset02 현재 위치 (블록의 시작)
src 0xoffset01 이전 위치 (블록의 마지막)
is_jump = 0
ii.
dst 0xoffset03 현재 위치
src 0xoffset02 이전 위치
is_jump = 0
iii.
dst 0xoffset05 현재 위치
src 0xoffset04 이전 위치 (이때 jmp, jz, jnz 등이었음, 당시에 is_jump 기록)
is_jump = 1 

dst와 src를 타겟 범위 내인지 먼저 판별하고 하나라도 tt이면 기록한다. 둘다 tf 일 경우 다음 과정을 생략한다
is_jump == 1 일 경우에만 
dst offset이 tt이고 타겟내의 함수 시작점이거나 dst offset이 tf이면
 추가로 기록한다(기본 call과 중복 기록 방지)
 ; dst offset이 tt이면서 함수시작점이 아닐경우 기록 안하는 이유는 내부 if 또는 switch 문일 수 있기 때문이다. 
 (컴파일러 최적화등 엣지 케이스는 고려 제외) 

추가적으로 둘다 tf 일 경우 call 및 ret 기록에서도 배제한다. (단, 절대 Stalker.exclude(range)를 사용하지 말 것
 이를 사용할 경우 해당 범위의 트레이스를 포기함과 더불어 tf에서 tt로 인바운드 되는 것을 놓친다)
